# 생산 가능 여부 확인 AI Agent (자재대응 Agent) 설계

## 목적과 이유

생산 담당자가 "내일 P-100을 20개 만들 수 있을까? 부족한 부품은 입고 예정까지 확인해줘"라고 물으면, Claude가 **필요한 자료를 스스로 골라 조회하고** 자재 기준 생산 가능 여부를 답하는 에이전트를 만든다. (출처: `실습_2.docx`)

- 용도: **실습 제출용 데모**. 평가자가 tkinter 앱을 켜고 대화 시나리오를 입력했을 때, 에이전트가 도구를 고르고 실행하는 과정과 판단 근거가 화면에 그대로 보이면 성공이다.
- 이 수업의 최종 목표는 A2A 프로젝트이고, 이 작업은 그 사전 작업 중 하나다. 단, **이번 범위에서 A2A(Agent Card, task 상태 등)는 고려하지 않는다** (사용자 결정). 에이전트 로직과 화면 코드를 분리하는 정도만 한다.

핵심 위험은 **그럴듯하지만 틀린 판정**이다. 시작 시각을 임의로 가정하거나, 오후 입고분을 오전 생산에 쓰거나, 이전 질문의 수량으로 답하거나, 조회 실패를 "입고 예정 없음"으로 착각하면 데모가 실패한다.

## 목표

1. Claude API **tool use**로 동작한다. 조회 순서를 코드로 고정하지 않고 Claude가 도구와 입력값을 고른다. Python은 도구를 실행해 결과를 돌려주고, Claude는 추가 조회하거나 답한다.
2. 도구 4개: `get_bom`, `get_inventory`, `get_inbound_schedule`, `calculate_shortage` (Python 함수, 자료는 로컬 CSV).
3. 부족량 등 **수량은 반드시 `calculate_shortage`로 계산**한다 (Claude가 암산한 수치를 답에 쓰지 않도록 지시).
4. 판단에 필요한 정보(생산 수량, 날짜, 시작 시각)가 빠지면 **사용자에게 묻는다**.
5. 실행한 도구·입력·결과를 화면에 보여준다.
6. 도구 실행은 **사용자 발화 한 건당** 최대 N회 (기본 16, 앱에서 8로 변경 가능). 후속 발화에서는 다시 센다.
7. 조회 실패 시 확인하지 못한 내용을 알려준다.
8. `참고/질문_모음.txt`의 9개 질문과 `대화_시나리오.txt`의 5개 대화가 기대 결과대로 동작한다.

## 비목표

- A2A 서버, Agent Card, 구조화된 기계용 응답 (사용자 결정: 아직 고려하지 않음)
- 실제 발주, 재고 CSV 수정 등 쓰기 도구
- 설비 능력·인력 판단 (답변의 가능 여부는 **자재 기준**)
- 엑셀(.xlsx) 입력 지원 (CSV만 사용, 내용 동일)
- `생산질문.csv` 20건 일괄 처리·대시보드 (이번 범위 아님)
- `추가상황/`(나누어 입고, 여러 부품 부족, 한도 12회), `결과예시/`, `오류상황/` — 폴더가 없어 범위에서 제외 (사용자 결정). 데이터 폴더 전환 기능도 만들지 않음

## 실패로 간주하는 것 (안티 목표)

- 시작 시각 없이 입고에 의존하는 판정을 내림 (예: "내일 P-100 20개 가능")
- 생산 시작 시각 이후에 도착하는 입고를 반영함 (오후 3시 입고분을 오전 9시 생산에 사용)
- 입고 예정을 "입고 완료"처럼, 또는 생산 일정이 실제로 변경된 것처럼 표현함 → 입고 반영 시 "예정대로 도착한다면" 조건부 표현
- 후속 질문("30개로 늘리면?")에서 이전 수량 기준 계산을 재사용함
- 등록되지 않은 제품(P-999)에 소요량을 지어냄
- 수량·날짜가 빠졌는데 20개나 내일을 임의로 적용함
- 입고 조회 **실패**를 "입고 예정 없음(빈 배열)"과 같게 취급함
- 한도를 넘어 도구를 실행함

## 제약

- Python 3.12, 공식 `anthropic` SDK 직접 사용 (LangChain 등 미사용 — 실습 요구가 "Claude API tool use")
- 모델 `claude-opus-5-5` (직전 프로젝트와 동일)
- API 키는 환경변수 또는 프로젝트 폴더 `.env`의 `ANTHROPIC_API_KEY` (`.env`는 git 제외, `.env.example` 제공)
- Windows 11, 한글 깨짐 없음. CSV는 `utf-8-sig`로 읽음
- 날짜·시각은 `+09:00`(Asia/Seoul) 포함 값으로 비교
- 데이터: `참고/` 폴더의 CSV(`제품별_소요부품.csv`, `현재재고.csv`, `입고예정.csv`, `제품목록.csv`)와 `실습설정.json`. `질문_모음.txt` 등 안내문은 입력 데이터로 읽지 않음

## 데이터와 기준값

- **기준시각** = `실습설정.json`의 `기준시각` (`2026-10-15T09:00:00+09:00`). "내일" = 2026-10-16. Claude에게 시스템 프롬프트로 기준시각을 알려 주고, 사용자 표현("내일 오후 4시")을 ISO 시각으로 바꾸게 한다.
- **실행 한도 기본값** = `실습설정.json`의 `최대도구실행횟수` (16). 앱에서 8/16 선택 가능. (사용자 결정)
- 재고 전량 사용 가능, 안전재고 미적용 (`실습설정.json`)
- 입고 반영 범위: **기준시각 이후 ~ 생산 시작 시각까지**의 입고 예정만 합산

## 도구 정의 (결정된 방식)

| 도구 | 입력 | 출력 |
|---|---|---|
| `get_bom(product_code)` | 제품코드 | 일치 행 목록(부품코드, 부품명, 제품1개당소요량, 단위). 없으면 "등록되지 않은 제품" 표시(오류가 아닌 정상 결과) |
| `get_inventory(part_code)` | 부품코드 **또는 부품명**("센서 B", 공백 무시 일치) | 부품코드, 부품명, 현재재고, 단위. 없는 부품이면 그렇게 표시 |
| `get_inbound_schedule(part_code, production_start?)` | 부품코드, 선택: 생산 시작 시각(ISO) | 입고 행 목록. 행이 없으면 빈 배열 `[]`(정상). `production_start`를 주면 각 행에 시작 전 도착 여부 표시 + 시작 전 입고 합계. **조회 실패 모드에서는 오류** 반환 |
| `calculate_shortage(part_code, production_qty, qty_per_unit, current_stock, inbound_before_start)` | 부품코드 + 정수 4개 | 부품코드, 필요수량, 현재부족량, 시작시각기준부족량 (`도구와_자료.txt` 공식) |

- `production_start` 선택 인자는 Claude의 판단: 시각 비교·합산을 LLM 암산에 맡기지 않기 위함. 실습 문서의 함수 이름·역할은 유지.
- 현재 재고만으로 충분한 부품은 입고 조회를 생략해도 된다 (`도구와_자료.txt`). 시스템 프롬프트로 안내.
- 생산 수량은 양의 정수만 허용. 음수·0·소수는 Claude가 되묻고, `calculate_shortage`도 잘못된 수량이면 오류를 돌려준다(이중 방어).

## 에이전트 동작

- 대화 기록은 [새 대화] 전까지 유지 (후속 발화 "오전 9시야", "30개로 늘리면?"가 앞 맥락을 이어받음).
- 사용자 발화 1건 처리 = Claude 호출 → `tool_use`면 도구 실행 후 `tool_result` 반환 → 반복 → 최종 텍스트 답변.
- 도구 오류는 `tool_result`에 `is_error: true`로 전달. Claude는 확인된 것(예: 현재 재고 기준 부족)과 확인하지 못한 것(입고 반영 판단)을 구분해 답한다.
- 한도 도달 시: 추가 도구를 실행하지 않고, Claude가 그때까지 확인한 내용으로 답하되 확인하지 못한 항목을 밝힌다.
- 답변 원칙(시스템 프롬프트): 자재 기준 판단임을 밝힘, 입고 반영 시 조건부 표현, 부품별 필요/재고/반영 입고/부족 수치 제시, 수치는 계산 도구 결과만 사용.

## 화면 (tkinter, 시안 A — 사용자 선택)

```
┌ [새 대화]  실행 한도 [16▾]  ☐ 입고 조회 실패 모드 ───────────────┐
│ 대화                               │ 도구 실행 기록                 │
│  (사용자) 내일 P-100을 20개…       │ 질문 1 · 도구 4/16회           │
│  (에이전트) 시작 시각이 언제인가요?│  ① get_bom("P-100") → …        │
│  (사용자) 오전 9시야.              │  ② get_inventory("BRG-A") → 30 │
│  (에이전트) 생산 불가 (자재 기준)… │ 질문 2 · 도구 1/16회           │
│  [판정 카드: 부품별 수치]          │  ① calculate_shortage(…) → …   │
│ [입력칸                 ][보내기]  │                                │
└──────────────────────────────────────────────────────────────────────┘
```

- 상단: [새 대화](대화·도구 기록 초기화), 실행 한도(16/8), 입고 조회 실패 모드 스위치(대화 5·질문 9 시연용)
- 왼쪽: 대화 말풍선, 입력칸, [보내기]/엔터
- 오른쪽: 사용자 발화별 묶음 "질문 n · 도구 k/N회", 실행 순서대로 `도구명(입력) → 결과 요약`, 오류 줄은 빨간색, 줄 클릭 시 결과 원문(JSON) 펼침
- 판정 카드: 생산 가능 여부를 다룬 답변에만, 가능/조건부 가능/불가/확인 불가를 색으로 구분 + 부품별 수치. 단순 재고 조회에는 없음
- API 호출은 백그라운드 스레드, 대기 중 "확인 중…" 표시, 화면 멈춤 없음
- API 키 없음·인증 실패·연결 실패는 대화창에 알기 쉬운 문구로 표시

## Claude가 정한 것 (검토 대상)

- `get_inbound_schedule`에 선택 인자 `production_start` 추가, 시작 시각과 **같은 시각 입고는 포함**("시작 시각까지")
- 판정 카드 데이터: 최종 답변 직후, 이번 발화에서 실행된 `calculate_shortage` 결과들로 카드를 만든다 (Claude가 별도 형식으로 출력하지 않음). 부품 연결을 위해 `calculate_shortage`에 `part_code` 인자를 추가(계산식은 실습 그대로). 판정 단계 표시는 Claude 답변에서 추출하지 않고 수치로 결정: 모든 부품 현재부족 0 → 가능, 현재부족>0이지만 시작시각기준부족 0 → 조건부 가능, 시작시각기준부족>0 → 불가, 현재부족>0인 부품 중 입고 조회가 오류였던 부품이 있으면 확인 불가
- 판정 카드 표시 조건: 이번 발화에서 `get_bom`으로 확인한 **모든 부품**에 `calculate_shortage` 결과가 있고, (a) 모든 부품 현재부족 0이거나 (b) 현재부족 부품에 대해 `production_start`를 준 입고 조회(또는 조회 오류)가 있을 때만 표시. 시작 시각을 되묻는 답변 옆에는 카드가 나오지 않는다
- `get_inventory`는 부품명도 받는다: "센서 B 재고만 알려줘"에 `get_inventory` 1회로 답하게 하기 위함 (BOM·입고 조회 불필요)
- 입고 조회 실패 모드: 스위치를 켜면 **모든** `get_inbound_schedule` 호출이 `is_error: true`와 `"입고 예정 조회 실패: 입고 시스템 응답 없음"`을 반환 (`오류상황/입고조회_실패.json`이 폴더에 없어 Claude가 정함)
- 검증 기준: `질문_모음.txt`의 → 기대 결과와 `실습_2.docx`·`대화_시나리오.txt`의 기대 동작(대화 2: 베어링 10개 부족 + 오후 3시 입고 시각 고려). 대화 3(오후 4시, 20개)은 질문 모음 4·5와 같은 계산: 조건부 가능
- 모델 `claude-opus-5-5`, 키는 `.env`
- 테스트 대상 데이터는 `참고/` CSV를 그대로 사용(복사하지 않음)
